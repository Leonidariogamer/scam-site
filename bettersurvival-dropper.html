The modpack with one extra file

  • Danger: high
  • Dropper
  • Minecraft 1.21.1 / Fabric

In one sentenceA modpack that looks like a legitimate CurseForge pack contains one unlisted mod. That mod is a downloader: when the game starts, it fetches the real malware from a file-sharing link.

Spot it, and what to do

How to spot it

  • The modpack's list names real mods, but there is one extra file in the mods folder that is not on the list.
  • The extra mod has a vague name and description, an official-sounding author ("Fabric Team"), and is only a few kilobytes. Real mods are usually megabytes.
  • It came from a chat message, not from the CurseForge or Modrinth page.
  • It arrived from a friend who "never sends files". Their account may be hacked.

If you already ran it

  • Look for a java folder inside %LOCALAPPDATA% containing services.jar. If it exists, treat the PC as infected.
  • Change passwords from a different, clean device. Email first, then Discord, Steam, Microsoft and your bank.
  • Sign out of all sessions, redo two-step login, and move any crypto to a new wallet — this one can silently swap wallet addresses you copy/paste, so double-check any crypto transfer you made while it was running.
  • Back up your files and reinstall Windows to be sure.

Technical details

For researchers: how it was analysed

The zip's manifest lists 19 genuine CurseForge projects. The extra file is overrides/mods/BetterSurvival.jar (6,337 bytes) with one class, com.example.mod.mc, in the default template package. It is obfuscated with ZKM (Zelix KlassMaster), which encrypts every string.

The strings were recovered statically by re-implementing the decryption routine from the class's bytecode, without executing the sample. The result is the chain in step 3 to 5: create %LOCALAPPDATA%\java, download java.zip from a file-sharing link, unpack and delete it, then run services.jar with the bundled javaw.exe. The download address is withheld here on purpose.

A second copy of the pack, sent a day later under a new filename (BetterCraft.jar), used the same structure with freshly randomised obfuscation constants. Decoding it the same way produced a new download link, which was still live. See the update below for what that led to.

A third-party sandbox run of the jar executed it as a plain Java program, so the Fabric start-up code never triggered. That is why it showed no behaviour.

Update: why the second stage stayed silent in testing, and what it actually does

Early tests of the second stage (services.jar) inside a virtual machine showed no network activity at all, even after letting it run for half an hour. Running the exact same unmodified file on a real, disposable computer with no virtual machine involved produced activity within seconds: it looked up a command-and-control address and checked in with it three times, and separately tried to contact Discord's real servers.

This confirms the program deliberately checks whether it's running inside a virtual machine or analysis sandbox before doing anything, and goes dormant if it thinks it is. Recovered from the program's own memory while it ran: it checks for dozens of known virtual-machine and sandbox driver files, process names, and even a huge list of computer names used by specific automated analysis services, plus an explicit, named check for Microsoft's own Hyper-V virtualization feature. This is a widely-reused checklist copied across many stealer kits, not something built specifically for this sample.

Also now confirmed directly, rather than assumed: it reads saved passwords out of Chrome/Edge's own password database (using the same Windows feature those browsers use to protect them, turned against the user), it specifically goes after Discord's local session files, it can silently replace whatever is on your clipboard (the classic trick for swapping a copied crypto wallet address for the attacker's own), and it can take screenshots. It also opens a plain window with scrolling text while it works, most likely to look like normal "loading" output and keep the victim from getting suspicious.

All of this was confirmed by reading what the program does and by observing its network traffic, never by using any data it collected. The command-and-control address it contacts is withheld here on purpose, same as the original download link.

Update: contact with an account linked to this malware

In October 2026, an account believed to be connected to this sample's distribution was contacted directly. What follows is self-reported by that account, and some of it did not hold up.

  • The account first claimed to write the malware themselves in Java, using a custom obfuscator on top of a commercial one. Later information instead points to a premade builder sold for around $300 within a Turkish group, so this looks like bragging rather than fact. The obfuscation is likely a feature of that kit, not original work.
  • They claim to test each build against a public scanning service before distributing it, aiming for zero detections.
  • They said the download link in this sample gets suspended whenever someone reports it, forcing a rebuild with a new link each time. That confirms reporting these links works — it costs a rebuild and a redistribution cycle, not just one deleted file.

Nothing here was obtained by running the malware, and nothing was shared with the account to help it evade detection or reporting further.

Update: the second stage (services.jar) was recovered and decompiled

A live download link from the second build (above) was followed statically: a 55 MB archive containing a portable Java runtime and the real payload, services.jar (12 MB). A separate attempt to read this file with ordinary tools reportedly used up 48 GB of memory without finishing.

The cause turned out to be a handful of individual program components deliberately bloated to the point that tools which try to reconstruct readable code from them run out of memory, rather than a huge number of components. Reading it one small piece at a time instead avoided the problem, and nearly the whole program was turned back into readable, if still obfuscated-looking, source code. No part of it was ever run.

Two plain-text markers found inside services.jar confirm it is a licensed, bought product rather than something the distributor wrote: a license code and a long reference number, sitting unencrypted in the file.

Confirmed directly in the code: it uses a library typically used to maintain a live connection to Discord, consistent with how the related "fake Fabric API" sample reports back to its operator. It also contains Windows system calls specifically used to detect and defeat an attached debugger, a standard anti-analysis measure.

What could not be recovered: the program's actual secrets (the address it reports to, names it uses to blend in, and so on) stay hidden behind their own obfuscation, and unlike the small first-stage mod, this one does not use one single trick for all of it. Different parts scramble their text in different ways, so there is no single fix that unlocks everything. This is where the analysis stopped.
